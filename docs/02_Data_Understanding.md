# Data Understanding

## 1. Dataset Overview

This project uses the public Google Analytics 4 (GA4) ecommerce dataset available through Google BigQuery.

### Dataset Information

| Attribute | Details |
|---|---|
| Google Cloud Project | `bigquery-public-data` |
| Dataset | `ga4_obfuscated_sample_ecommerce` |
| Dataset Location | US |
| Data Type | GA4 event-level ecommerce data |
| Table Pattern | `events_YYYYMMDD` |
| Analysis Period | November 1, 2020 to January 31, 2021 |
| Number of Daily Tables | 92 |

The dataset contains event-level data representing user interactions with an ecommerce platform. Each event represents an interaction performed by a user, such as viewing a page, viewing a product, adding a product to the cart, beginning checkout, or completing a purchase.

The data is stored across daily event tables following the naming pattern:

`events_YYYYMMDD`

For example:

- `events_20201101`
- `events_20201102`
- `events_20201231`
- `events_20210131`

For analysis across multiple dates, the daily tables can be queried using the wildcard table pattern:
`bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`

The dataset provides information about users, events, ecommerce transactions, products, devices, geographic attributes, and traffic sources. This makes it suitable for analyzing customer behavior, conversion funnels, product performance, revenue, acquisition channels, retention, and other e-commerce business metrics.

## 2. Dataset Structure

The GA4 ecommerce dataset follows an event-based data model.

Each row represents a single event generated by a user interaction with the ecommerce platform.

The main structure can be represented as:

User
→ Event
→ Event Parameters
→ Ecommerce Information
→ Product Items

In addition to event and ecommerce information, the dataset also contains device, geographic, traffic-source, and user-level information.

### Top-Level Fields

The event tables contain the following major top-level fields:

| Field | Type | Description |
|---|---|---|
| `event_date` | STRING | Date on which the event occurred |
| `event_timestamp` | INTEGER | Timestamp of the event |
| `event_name` | STRING | Name of the event or user interaction |
| `event_params` | RECORD (REPEATED) | Additional parameters associated with  the event |
| `event_value_in_usd` | FLOAT | Event value in USD, when available |
| `user_id` | STRING | User identifier, when available |
| `user_pseudo_id` | STRING | Pseudonymous identifier used for user-level analysis |
| `user_properties` | RECORD (REPEATED)| Additional user-level properties |
| `user_first_touch_timestamp` | INTEGER | Timestamp of the user's first recorded interaction |
| `user_ltv` | RECORD | User lifetime value information, when available |
| `device` | RECORD | Device and operating-system information |
| `geo` | RECORD | Geographic information |
| `app_info` | RECORD | Application-related information |
| `traffic_source` | RECORD | Traffic and acquisition source information |
| `stream_id` | INTEGER | Data stream identifier |
| `platform` | STRING | Platform associated with the event |
| `event_dimensions` | RECORD | Additional event dimensions |
| `ecommerce` | RECORD | Ecommerce transaction information |
| `items` | RECORD (REPEATED) | Product-level information associated with the event |

Other technical fields such as `event_previous_timestamp`, `event_bundle_sequence_id`, `event_server_timestamp_offset`, and `privacy_info` are also available and may be used where relevant.

## 3. Nested and Repeated Fields

The GA4 dataset contains both standard fields and nested/repeated RECORD fields.

This structure allows GA4 to store detailed information about events, users, transactions, and products within a single event-level record.

### Nested Fields

Some fields are stored as RECORD structures containing multiple related fields.

Important nested fields include:

- `device`
- `geo`
- `traffic_source`
- `ecommerce`
- `event_params`
- `user_properties`
- `items`

For example, the `ecommerce` field contains transaction-level information such as:

- `transaction_id`
- `purchase_revenue`
- `total_item_quantity`
- `unique_items`
- `tax_value`
- `shipping_value`
- `refund_value`

### Repeated Fields

Some RECORD fields are also repeated, meaning a single event can contain multiple records.

The main repeated fields are:

- `event_params`
- `user_properties`
- `items`

For example, a single ecommerce event may contain multiple products:

```text
Event
│
└── items
    ├── Product 1
    ├── Product 2
    └── Product 3
```
Similarly, an event can contain multiple event parameters:

```text
Event
│
└── event_params
    ├── Parameter 1
    ├── Parameter 2
    └── Parameter 3
```
### `event_params` Structure
The event_params field contains two main components:

```text
event_params
├── key
└── value
    ├── string_value
    ├── int_value
    ├── float_value
    └── double_value
```

### `items` Structure

The `items` field contains product-level information and is stored as a repeated RECORD.

Important product fields include:

- `item_id`
- `item_name`
- `item_brand`
- `item_variant`
- `item_category`
- `price`
- `quantity`
- `item_revenue`
- `item_refund`
- `coupon`
- `promotion_name`

A single event can contain multiple products:

```text
Event
│
└── items
    ├── Product 1
    ├── Product 2
    └── Product 3 
```

This structure is important for product-level analysis because product metrics such as revenue, quantity, refunds, categories, and product performance are stored within the repeated `items` records.

### Why Nested and Repeated Fields Matter

Understanding nested and repeated fields is essential for this project because several business analyses depend on extracting information from these structures.

Examples include:

- Product analysis using `items`
- Event parameter analysis using `event_params`
- Revenue analysis using `ecommerce`
- Device analysis using `device`
- Geographic analysis using `geo`
- Marketing analysis using `traffic_source`

The use of nested and repeated fields makes GA4 analysis more complex than a traditional flat relational dataset and requires BigQuery-specific SQL techniques such as `UNNEST()`.

## 5. Ecommerce Data Structure

The GA4 dataset contains dedicated ecommerce information through the `ecommerce` and `items` fields.

The `ecommerce` field stores transaction-level information, while the repeated `items` field stores product-level information associated with an event.

### Ecommerce Transaction Fields

The `ecommerce` RECORD contains the following fields:

| Field | Type | Description |
|---|---|---|
| `total_item_quantity` | INTEGER | Total quantity of items associated with the transaction/event |
| `purchase_revenue_in_usd` | FLOAT | Purchase revenue in USD |
| `purchase_revenue` | FLOAT | Purchase revenue |
| `refund_value_in_usd` | FLOAT | Refund amount in USD |
| `refund_value` | FLOAT | Refund amount |
| `shipping_value_in_usd` | FLOAT | Shipping value in USD |
| `shipping_value` | FLOAT | Shipping value |
| `tax_value_in_usd` | FLOAT | Tax value in USD |
| `tax_value` | FLOAT | Tax value |
| `unique_items` | INTEGER | Number of unique items associated with the transaction |
| `transaction_id` | STRING | Identifier for the transaction |

These fields will support revenue, transaction, order value, refund, tax, shipping, and sales analysis.

### Product-Level Data

The repeated `items` RECORD contains detailed information about products associated with an event.

Important product attributes include:

| Field | Description |
|---|---|
| `item_id` | Product identifier |
| `item_name` | Product name |
| `item_brand` | Product brand |
| `item_variant` | Product variant |
| `item_category` | Main product category |
| `price` | Product price |
| `quantity` | Quantity associated with the item |
| `item_revenue` | Revenue generated by the item |
| `item_refund` | Refund amount associated with the item |
| `coupon` | Coupon associated with the item |
| `promotion_name` | Promotion associated with the item |

The `items` field is repeated because a single ecommerce event can contain multiple products.

This structure enables detailed product-level analysis, including:

- Product sales performance
- Product revenue contribution
- Product quantity analysis
- Category performance
- Brand performance
- Product refunds
- Promotion and coupon analysis

### Relationship Between Ecommerce and Items

The relationship between transaction-level and product-level information can be represented as:

```text
Ecommerce Event
│
├── ecommerce
│   ├── transaction_id
│   ├── purchase_revenue
│   ├── total_item_quantity
│   ├── unique_items
│   ├── tax_value
│   └── shipping_value
│
└── items[]
    ├── item_id
    ├── item_name
    ├── item_category
    ├── price
    ├── quantity
    └── item_revenue
```

## 7. Data Quality Checks

Before performing detailed business analysis, the dataset will be evaluated for completeness, consistency, and potential data-quality issues.

The purpose of these checks is to understand the limitations of the available data and identify fields that may require filtering, transformation, or special handling during analysis.

### 7.1 Event Date Completeness

The analysis period will be checked to ensure that the expected daily event tables and event dates are available.

The dataset contains daily tables following the `events_YYYYMMDD` pattern.

### 7.2 Missing User Identifiers

The `user_pseudo_id` field will be checked for missing values because it is used for user-level analysis.

Missing user identifiers may affect:

- User counts
- Customer behavior analysis
- Funnel analysis
- Retention analysis
- Customer segmentation

A completeness check was performed on the `user_pseudo_id` field across the full analysis dataset.

|---|---:|

| Missing User IDs | 0 |
| Missing User ID Percentage | 0.00% |

No missing `user_pseudo_id` values were identified. Therefore, the field can be used reliably as the primary pseudonymous identifier for user-level analysis within this dataset.

### 7.3 Missing Event Names

The `event_name` field will be checked for null or missing values.

Because event names define the type of user interaction, missing event names could affect event-level and funnel analysis.

The number of purchase events is higher than the number of unique transaction IDs. This indicates that some transaction IDs are associated with multiple purchase events.

Therefore, purchase event count and transaction count will be treated as different metrics.

For transaction-level analysis, distinct transaction IDs will be used where transaction identifiers are available:

`COUNT(DISTINCT ecommerce.transaction_id)`

This approach helps avoid overcounting transactions when multiple purchase events are associated with the same transaction ID.

### 7.9 Data Quality Handling Approach

The original GA4 source data will not be modified during the analysis.

Data-quality issues will be handled at the analytical level based on the requirements of each metric.

- **Missing `user_pseudo_id`:** No missing values were identified, so no filtering is required for user-level analysis.

- **Missing `event_name`:** No missing event names were identified, so all events can be included in event-level analysis.

- **Missing `transaction_id`:** Purchase events without a transaction ID will not be treated as unique transactions. Transaction-level metrics will use available distinct transaction IDs.

- **Missing purchase revenue:** Purchase events with missing revenue will not be treated as zero-revenue transactions. Revenue-based calculations will use records with available revenue values, with the limitation documented.

- **Empty `items` arrays:** Purchase events without product items will be excluded from product-level analysis where item-level information is required.

- **Device, geographic, and traffic-source data:** No missing values were identified in the primary dimensions checked, so these fields can be used directly for segmentation and comparison.

- **Potential duplicates:** No duplicate event combinations were identified using the selected duplicate-checking fields.

Any filters or transformations applied during the SQL and Python analysis will be documented so that the analytical process remains transparent and reproducible.

## 8. Data Limitations and Analytical Considerations

The GA4 public ecommerce dataset provides a useful foundation for e-commerce analysis, but several limitations should be considered when interpreting the results.

### 8.1 Public Sample Dataset

The analysis is based on a public GA4 sample dataset rather than a complete enterprise production dataset.

Therefore, the findings should be interpreted as analytical findings from the available sample data and should not be treated as a representation of the performance of a specific real-world business.

### 8.2 User Identification

User-level analysis uses the `user_pseudo_id` field as the available pseudonymous user identifier.

This identifier does not represent personally identifiable customer information and may not represent a customer across different devices or environments.

### 8.3 Missing Transaction Information

A small number of purchase events do not contain a `transaction_id`.

Therefore, transaction-level analysis will rely on available distinct transaction IDs and will clearly document this limitation.

### 8.4 Missing Revenue Information

Some purchase events do not contain purchase revenue.

These records cannot be reliably used for revenue-based calculations unless an appropriate methodology is available.

Missing revenue values will not automatically be interpreted as zero revenue.

### 8.5 Marketing Attribution Limitations

The available dataset contains traffic-source information, but detailed advertising cost information is not available.

Therefore, metrics such as true ROAS, cost per acquisition, and campaign profitability cannot be reliably calculated.

### 8.6 Profitability Limitations

The dataset provides revenue-related information but does not provide sufficient information about product costs, operating expenses, or profit margins.

Therefore, profitability and net profit analysis are outside the scope of this project.

### 8.7 Customer Lifetime Value Limitations

Customer Lifetime Value (CLV) can only be estimated using information available within the dataset.

Because the available analysis period is limited, long-term customer value may not be fully observable.

Any CLV methodology used in the project will therefore be treated as an estimate rather than an exact measure of future customer value.

### 8.8 Causality

Observed relationships and patterns in the data will not automatically be interpreted as causal relationships.

The analysis will identify correlations, trends, and behavioral patterns, while business recommendations will be based on evidence supported by the available data.

### 8.9 Analytical Scope

All conclusions and recommendations will remain within the scope of the available GA4 data.

Business factors that cannot be observed through the dataset, such as operational costs, inventory constraints, offline purchases, or customer support interactions, will not be assumed without supporting evidence.

### 8.10 Overall Consideration

The dataset is suitable for analyzing e-commerce customer behavior, product performance, revenue, acquisition channels, conversion funnels, device performance, geographic patterns, and retention-related behavior.

However, the limitations described above will be considered throughout the SQL, Python, visualization, and business-insight stages of the project.
